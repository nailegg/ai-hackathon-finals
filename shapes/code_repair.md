# Shape: 기존 코드 수리

> **대상: 에이전트 참고 — 지시가 아니다.** 지시는 과제 루트의 AGENTS.md와 CONTRACT.md가 우선한다. CONTRACT §10에 이 파일 경로가 적혀 있을 때만 읽는다.

**적용:** 제공된 저장소의 실패 테스트·버그·장애 재현이 입력인 과제. **새 프로젝트를 만들지 않는다.** 기존 소스와 실패 테스트가 있으면 다른 신호가 있어도 이 형태다.

## 판별 신호
- 과제 폴더에 기존 소스 트리, `tests/`, `requirements.txt`/`package.json`이 있음
- "실패하는 테스트를 통과시켜라", "버그를 고쳐라", "장애를 재현하고 수정" 문구
- 이슈 목록·에러 로그·재현 절차 제공
- 채점이 테스트 통과 수나 특정 동작 복구로 설명됨

## 산출물 형태
- 채점자가 먼저 볼 것: 테스트 실행 결과(통과/실패 수)와 `git diff --stat`
- 수정된 저장소 그 자체. 테스트 파일은 수정하지 않음
- 수정 요약(AC별 원인·수정·검증)

## 붙일 부록 (과제 루트 파일명. §10 '붙인 부록' 줄에 이 이름으로 적는다)
- `REPAIR_MAP.md` (실패 → 재현 명령 → 관련 파일 → 원인 후보 → 상태)

## Baseline
- 가장 비중 큰 실패 1개를 재현하는 명령을 먼저 확보. 통과시키는 것보다 재현이 먼저
- 패치는 한 함수·한 파일 단위. 리팩터링 금지

## 독립 검증
- 수정 전 실패 → 수정 후 통과, 그리고 다른 테스트가 새로 실패하지 않음
- 테스트 파일 변경 0, 포맷 일괄 변경 0
- 예시 AC 검증 명령: `pytest -q tests/test_x.py::test_y` 통과; `pytest -q` 전체 결과 비교; `git diff --stat -- tests/` 출력 없음

## 지표
> §6 "지표 정의"가 비어 있을 때 §9 가정으로 제안할 후보다. §6에 정의가 있으면 그것만 계산한다.

- 주: 통과한 AC(테스트) 수, 회귀 0
- 보조: 변경 줄 수(작을수록 좋음), 미해결 항목의 원인 후보 기록
- 함정 지표: 테스트를 고쳐서 얻은 통과

## 흔한 함정
- 재현 전에 광범위 리팩터링
- 테스트나 fixture를 수정해 통과시킴
- 의존성 버전 문제를 코드 버그로 착각(또는 그 반대)
- 한 패치로 여러 실패를 동시에 고치려다 회귀
- 디버그 출력·주석 처리 코드가 남음
- 새 프로젝트를 옆에 만들기 시작

## 쓸 snippets
- 대개 없음. 데이터 처리 버그면 `csv_load`의 인코딩·타입 처리 참고

## 참고 시나리오 카드
과제 루트에 `CARD_REF.md`가 있을 때만 그 파일을 읽는다. 카드 원본은 읽지 않는다. 도메인 용어는 §10에 용어집 절이 적혀 있을 때만 그 절을 읽는다.

## 만들지 않을 것
- 새 프로젝트, 구조 변경, 테스트 재작성, 대규모 포맷팅

코드베이스가 크고 실패가 여럿이라 원인 탐색이 수정을 막을 때만. 사람이 Terminal 2에서 `prompts/specialists/specialist-debug.md`로 띄운다. 동시 1개, 10분, 읽기 전용, 결과는 과제 루트 `REPAIR_MAP.md` 한 파일. 수정하는 세션은 Main 하나다.
