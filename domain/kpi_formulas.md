# KPI 정의식과 계산 함정 — 이 숫자가 어떤 질문에 답하는가

> **대상: 사람(학습)과 에이전트(참조).** CONTRACT §6 핵심 계산의 지표를 정할 때와 §7 AC의 기대 결과를 쓸 때 본다. 절마다 "이 숫자들이 왜 있나"를 먼저 두고 정의식 표를 둔다. 표의 "함정" 열은 그 지표를 계산할 때 틀리기 쉬운 지점이고, 그 아래 설명이 왜 틀리는지다. 과제 README가 지표를 정의하면 README가 우선하고, 다르게 계산했다면 §9 가정에 적는다.

---

## KPI를 계산하기 전에 알아야 할 것

**KPI는 "비율" 아니면 "시간"이다.** 이 문서의 지표 대부분은 두 숫자를 나눈 비율(수율, 가동률, 정밀도)이거나 두 시각의 차이(Cycle time, MTTR, Tardiness)다. 그래서 틀리는 방식도 둘이다. **분모를 잘못 잡거나**, **시각의 기준·단위를 잘못 잡거나.** 어떤 지표를 보든 "분모가 뭐지, 단위가 뭐지"를 먼저 물으면 함정의 절반을 피한다.

**집계 단위를 먼저 정한다.** 같은 "수율"이라도 Lot별, Tool별, 일별로 집계하면 다른 표가 나온다. 과제가 어느 단위를 원하는지(채점자가 볼 표의 행이 무엇인지) 정한 뒤 계산한다. 표의 "집계 단위" 열이 흔히 쓰는 단위다.

**비교는 같은 조건끼리.** Tool A와 B의 수율이 다르다고 A가 나쁜 것이 아니다. A가 어려운 제품만 처리했을 수 있다. 그래서 비교표에는 항상 "같은 Recipe·제품끼리 묶었는가"와 "표본 수가 몇인가"를 함께 적는다.

### 공통 함정 (모든 KPI에 해당)

| 함정 | 증상 | 예방 |
|---|---|---|
| 1:N 조인 후 합계 | Lot(1) : Wafer(25) 조인 뒤 Lot 수량 합이 25배 | 조인 전후 행 수를 출력, 집계 단위에서 먼저 집계한 뒤 조인 |
| 분모 0 | 투입 0인 Tool·Shift에서 NaN/inf | 분모 0은 `None`으로 두고 표에 "집계 불가" 표시 |
| Recipe/제품 mix | Tool A 수율이 낮은데 사실 어려운 제품만 처리 | 같은 Recipe·제품끼리 비교(층화), 표본 수 함께 표시 |
| 시간대·단위 | UTC/KST 9시간 차, 초/밀리초, 분/시간 혼용 | 로드 직후 하나의 단위·시간대로 변환하고 §4에 기록 |
| 미래 정보 누수 | 예측 시점 이후 검사 결과가 feature에 포함 | `time_split`, 예측 시점 이전 데이터만 사용 |
| 중복 행 | 같은 `(lot_id, step_id)`가 재작업으로 2번 | 기본키 유일성 검사, 재작업은 `rework_flag`로 분리 |

**왜 1:N 조인이 가장 위험한가.** Lot 표에는 "이 Lot은 Wafer 25장"이라는 숫자가 한 줄에 있다. Wafer 표에는 그 Lot의 Wafer가 25줄이다. 둘을 `lot_id`로 조인하면 Lot 표의 한 줄이 25번 복사된다. 그 상태에서 Lot 수량을 합치면 25배가 된다. 수율처럼 보이는 숫자가 2500%가 나오면 바로 알아채지만, 분자와 분모가 같이 25배 되어 비율은 멀쩡한데 절대량만 틀린 경우는 눈치채기 어렵다. 그래서 "조인 전 행 수, 조인 후 행 수"를 항상 출력한다.

## 1. 품질

**이 숫자들이 답하는 질문.** "만든 것 중 얼마나 쓸 수 있나(수율)", "버린 건 얼마나 되나(Scrap)", "다시 한 건 얼마나 되나(Rework)", "공정이 규격 안에 안정적으로 들어오나(Cp/Cpk)". 반도체 공장에서 가장 중요한 숫자이고, 과제에서 대시보드나 분석 보고서를 요구하면 거의 반드시 들어간다.

**수율에서 가장 헷갈리는 것은 "무엇의 수율인가"다.** Wafer 수율은 "Wafer 25장 중 몇 장이 살아남았나"이고, Die 수율은 "Wafer 위 칩 1000개 중 몇 개가 양품인가"다. 둘은 다른 숫자이고 같은 Lot에서 Wafer 수율 100%, Die 수율 85%가 동시에 나올 수 있다. Die 수율을 Wafer별로 구한 뒤 단순 평균하면 틀린다. Wafer마다 Die 수가 다르면 Die 수로 가중해야 한다.

| KPI | 정의식 | 집계 단위 | 함정 | 코드 힌트 |
|---|---|---|---|---|
| Wafer yield | 양품 Wafer 수 / 투입 Wafer 수 | Lot, Tool, 일 | Scrap을 분모에서 빼면 과대평가 | `good_wafers / total_wafers` |
| Die yield | 양품 Die 수 / 전체 Die 수 | Wafer, Lot | Wafer별 Die 수가 다르면 단순 평균 금지, Die 수로 가중 | `good_die.sum() / total_die.sum()` |
| Bin ratio | 해당 Bin 수 / 테스트 수 | Lot, Tester, Program | Soft bin과 Hard bin 혼용 | `groupby(['lot_id','hard_bin']).size() / n` |
| Scrap rate | 폐기 Wafer 수 / 투입 Wafer 수 | Lot, Step | 사유 코드 결측 | `scrap_flag.mean()` |
| Rework rate | 재작업 건수 / 처리 건수 | Step, Tool | 재작업을 처리 건수에 중복 계산 | 원 처리와 재작업을 구분한 뒤 비율 |
| Defect density | 결함 수 / 면적(cm²) | Wafer | 면적 단위 mm² vs cm² | `defects / area_cm2` |
| Cp | (USL − LSL) / (6σ) | 측정 항목 | Spec 없는 항목에 계산 | `(usl-lsl)/(6*std)` |
| Cpk | min(USL − μ, μ − LSL) / (3σ) | 측정 항목 | σ가 0이면 inf | `min(usl-mean, mean-lsl)/(3*std)` |

**Cp와 Cpk는 무엇인가.** 규격이 "두께 100±5nm"라면 허용 폭은 10nm다. 공정의 산포(6σ)가 5nm면 Cp = 2로, 폭의 절반만 쓰고 있으니 여유가 있다. 그런데 평균이 104nm에 치우쳐 있으면 위쪽 규격(105)까지 1nm밖에 안 남는다. 이 치우침까지 반영한 것이 Cpk다. Cp는 좋은데 Cpk가 나쁘면 "산포는 작지만 중심이 틀어졌다"는 뜻이고, 조치는 산포를 줄이는 것이 아니라 중심을 옮기는 것이다. 보통 Cpk 1.33 이상을 안정으로 본다.

## 2. 설비

**이 숫자들이 답하는 질문.** "장비가 쓸 수 있는 상태로 얼마나 있었나(Availability)", "쓸 수 있을 때 제 속도로 돌았나(Performance)", "돌린 것 중 양품은 얼마나(Quality)", 그리고 셋을 곱한 "장비를 종합적으로 얼마나 잘 썼나(OEE)". 고장 쪽은 "얼마나 자주 고장 나나(MTBF)"와 "고장 나면 얼마나 걸려 고치나(MTTR)".

**OEE는 곱이 아니라 세 요소로 본다.** OEE 60%라는 숫자 하나로는 무엇을 고쳐야 할지 모른다. Availability 80% × Performance 90% × Quality 83%인지, 95% × 65% × 97%인지에 따라 조치가 완전히 다르다(앞은 수율, 뒤는 속도). 그래서 표에는 세 요소를 따로 적고 OEE는 마지막 열에 둔다.

**PM을 다운타임에 넣을지는 README가 정한다.** 계획 정비(PM)도 장비가 안 돌아가는 시간이지만, "계획된 것이니 가동률에서 빼지 말자"는 공장도 있고 "안 돌아간 건 안 돌아간 것"이라는 공장도 있다. 두 정의 중 어느 쪽인지 README에서 찾고, 없으면 §9에 가정으로 적는다.

| KPI | 정의식 | 집계 단위 | 함정 | 코드 힌트 |
|---|---|---|---|---|
| Availability (가동률) | (총 시간 − 다운타임) / 총 시간 | Tool, 일/주 | PM(계획)과 BM(비계획)을 합산할지 README 확인 | `1 - downtime_h / total_h` |
| Performance (성능) | 실제 처리량 / 이론 처리량 | Tool | 이론 처리량(Recipe별 시간)이 없으면 계산 불가, §9 가정 | `actual_units / (run_h * ideal_rate)` |
| Quality (품질) | 양품 수 / 처리 수 | Tool | 수율과 같은 분모 문제 | |
| OEE | Availability × Performance × Quality | Tool | 세 값을 각각 보고, 곱만 보여주지 않는다 | `a*p*q` |
| MTBF | 가동 시간 합 / 고장(BM) 횟수 | Tool | 고장 0회면 분모 0 | `uptime_h / n_failures` |
| MTTR | 수리 시간 합 / 고장 횟수 | Tool | 수리 중 대기(부품 입고 대기) 포함 여부 | `repair_h.sum() / n_failures` |
| PM 준수율 | 기한 내 수행 PM 수 / 예정 PM 수 | Tool, 월 | 기한 정의(일 기준·Wafer 수 기준) | `(done_at <= due).mean()` |
| 부품 재고 지표 | 재고일수 = 재고량 / 일평균 소비량, 결품률 = 결품 건수 / 요청 건수 | 부품 | 소비 0인 부품은 재고일수 inf | |

**MTBF와 MTTR의 분모는 둘 다 "고장 횟수"다.** 분자가 다르다. MTBF는 고장과 고장 사이에 정상으로 **돌아간** 시간을 모아 고장 횟수로 나눈 것이고, MTTR은 고장 나서 **멈춰 있던** 시간을 모아 고장 횟수로 나눈 것이다. 어떤 장비가 한 달(720시간) 중 3번 고장 나 총 12시간 멈췄다면 MTBF = 708/3 = 236시간, MTTR = 12/3 = 4시간이다. 고장이 한 번도 없으면 분모가 0이라 "집계 불가"로 둔다. MTTR에서 "부품이 없어 기다린 시간"을 수리 시간에 넣을지는 README를 따른다. 넣으면 재고 문제가 MTTR로 보이고, 빼면 순수 수리 능력만 보인다.

## 3. 생산·흐름

**이 숫자들이 답하는 질문.** "지금 라인에 얼마나 쌓여 있나(WIP)", "하나 만드는 데 얼마나 걸리나(Cycle time)", "하루에 얼마나 나오나(Throughput)", "어디서 기다리나(Queue time)". 공장을 물이 흐르는 관으로 보면, WIP는 관 속의 물의 양, Throughput은 나오는 속도, Cycle time은 한 방울이 통과하는 시간이다. 셋은 묶여 있어서(리틀의 법칙: WIP ≈ Throughput × Cycle time) 하나가 이상하면 나머지도 확인한다.

**WIP는 "시점"의 숫자다.** 하루 동안 라인을 지난 Lot 수가 아니라, 어느 순간에 라인 안에 있는 Lot 수다. 그래서 "일별 WIP"는 매일 같은 시각(예: 자정)에 찍은 스냅샷이고, 하루치를 합치는 것이 아니다. `start <= t < end`인 Lot을 세면 된다.

| KPI | 정의식 | 집계 단위 | 함정 | 코드 힌트 |
|---|---|---|---|---|
| WIP | 시점 t에 라인에 있는 Lot 수 | 시점, Step | 시점별 스냅샷. 기간 합계가 아니다 | `((start<=t)&(end>t)).sum()` |
| Cycle time | 완료 시각 − 투입 시각 | Lot | 재작업 Lot은 꼬리가 길다. 중앙값도 함께 | `(end_at - start_at)` |
| Throughput | 기간 내 완료 Lot(또는 Wafer) 수 / 기간 | 일, 주 | 완료 기준(마지막 Step 종료)을 명시 | `completed.groupby(date).size()` |
| Queue time | 설비 앞 대기 시간 = 처리 시작 − 도착 | Step, Tool | 반송 시간 포함 여부 | |
| Utilization (가동률·활용률) | 처리 시간 합 / 가용 시간 | Tool | Availability(시간가동률)와 혼동. Availability는 "고장 안 나서 쓸 수 있었던 시간 비율", Utilization은 "그중 실제로 일한 비율" | |

**Cycle time은 평균만 보면 속는다.** 대부분 Lot이 10일에 끝나는데 재작업 Lot 몇 개가 30일 걸리면 평균이 12일로 올라간다. 평균 12일을 보고 "느려졌다"고 하면 틀린 진단이다. 중앙값(10일)과 90퍼센타일을 함께 적으면 "대부분은 그대로, 꼬리가 길어졌다"가 보인다.

**Availability와 Utilization은 한국어로 둘 다 "가동률"이라 가장 많이 섞인다.** Availability는 "고장·정비로 못 쓴 시간을 뺀 비율", 즉 쓸 수 있었던 시간이다. Utilization은 그 쓸 수 있었던 시간 중 실제로 Lot을 처리한 비율이다. 장비가 멀쩡한데 일감이 없어 놀았다면 Availability는 높고 Utilization은 낮다. README에 "가동률"이라고만 적혀 있으면 어느 쪽인지 정의식으로 확인하고 §9에 적는다.

## 4. 스케줄링·최적화

**이 숫자들이 답하는 질문.** 스케줄이나 배정 결과를 평가할 때 둘을 차례로 묻는다. 첫째, **유효한가.** 겹치는 작업, 없는 장비, 순서 위반 같은 hard constraint 위반이 하나라도 있으면 점수를 따질 자격이 없다. 둘째, 유효하다면 **얼마나 좋은가.** 납기를 얼마나 어겼나(Tardiness), 전체가 언제 끝나나(Makespan), 얼마나 움직였나(거리).

**위반 수가 0인지부터 본다.** 최적화 과제에서 가장 흔한 실수는 점수가 좋은 스케줄을 만들어 놓고 제약을 하나 어긴 것이다. 채점기는 보통 위반이 있으면 0점 처리한다. 그래서 점수를 계산하는 코드와 **별도로** 제약 위반을 세는 검증기(`validate_schedule`)를 만들고, 그것이 0을 돌려줄 때만 점수를 본다.

| KPI | 정의식 | 함정 | 코드 힌트 |
|---|---|---|---|
| Tardiness (지연) | max(0, 완료 − 납기) | 조기 완료는 0, 음수 아님 | `max(0, end - due)` |
| Total / Weighted tardiness | Σ 지연, Σ 우선순위 × 지연 | 가중치 단위 명시 | `sum(w * max(0, end-due))` |
| Number of tardy jobs | 지연 > 0인 작업 수 | | |
| Makespan | 마지막 작업 완료 시각 − 시작 기준 시각 | 시작 기준(0 또는 첫 release) | `max(end) - t0` |
| Flow time | 완료 − 투입(release) | Cycle time과 동일 개념 | |
| 총 이동 거리·시간 (VRP) | Σ 구간 거리 | 왕복·복귀 포함 여부 | |
| 제약 위반 수 | hard constraint 위반 건수. **0이어야 유효해** | 점수보다 먼저 확인 | `validate_schedule` |
| 개선율 | (baseline − 결과) / baseline | 분모 0, 방향(최소화/최대화) | |

**Tardiness는 "늦은 만큼"만 센다.** 납기보다 일찍 끝나면 0이지 음수가 아니다. 일찍 끝난 작업의 음수가 늦은 작업의 양수를 상쇄하면 "평균 지연 0"이라는 거짓 숫자가 나온다. 그래서 정의식에 max(0, ·)가 있다. 가중 지연은 "급한 Lot을 늦추면 더 크게 벌점"을 주는 것으로, 가중치가 우선순위 등급(1~5)인지 Lot 가치(원)인지 단위를 적어야 비교가 된다.

**개선율은 방향을 먼저 정한다.** 지연·거리처럼 작을수록 좋은 지표는 (baseline − 결과)/baseline이 양수면 개선이고, 처리량처럼 클수록 좋은 지표는 부호가 반대다. baseline이 0이면(지연이 원래 없었으면) 계산할 수 없으니 절대값 차이로 적는다.

## 5. 예측·분류 (불균형 데이터 기준)

**이 숫자들이 답하는 질문.** 불량을 맞히는 모델을 평가할 때 "맞힌 비율(Accuracy)"은 거의 쓸모가 없다. 불량률이 0.5%면 전부 "양품"이라고 답해도 Accuracy 99.5%다. 대신 묻는 것은 둘이다. **경보를 울렸을 때 진짜 불량인 비율**(Precision)과, **진짜 불량 중 경보로 잡은 비율**(Recall). 둘은 보통 반비례해서, 임계값을 낮추면 Recall이 오르고 Precision이 떨어진다.

**혼동행렬을 항상 먼저 그린다.** 2×2 표 하나(실제 양성/음성 × 예측 양성/음성)에서 모든 지표가 나온다. 표를 보여 주면 채점자가 어떤 지표든 직접 확인할 수 있고, 표를 안 보여 주고 F1만 적으면 임계값을 어디에 뒀는지 알 수 없다.

| 지표 | 정의 | 언제 | 함정 |
|---|---|---|---|
| 혼동행렬 | TP/FP/FN/TN 표 | 항상 먼저 | Accuracy만 보고하면 불량률 0.5%에서 99.5%가 나온다 |
| Precision | TP / (TP+FP) | 경보당 적중률 | |
| Recall | TP / (TP+FN) | 불량을 놓치지 않기 | |
| F1 | 2PR/(P+R) | 둘의 균형 | 임계값에 따라 바뀜, 임계값 명시 |
| PR-AUC | Precision-Recall 곡선 아래 면적 | 희소 양성 | ROC-AUC는 불균형에서 낙관적 |
| Recall@K | 점수 상위 K건에 포함된 양성 수 / 전체 양성 수 | 점검 인력이 K건만 볼 때 놓치는 불량 | Precision@K(상위 K건 중 양성 비율)와 다르다. K는 업무 기준으로 정해 §9에 |
| Precision@K | 점수 상위 K건 중 실제 양성 비율 | 경보 K건의 적중률 | Recall@K와 함께 제시 |
| Detection lead time | 실제 불량 발생(또는 검사 확정) 시각 − 이상 탐지 시각 | 조기 탐지. 양수가 클수록 일찍 잡음 | 음수면 사후 탐지. 부호 정의를 §6에 명시 |

**어느 지표를 주로 볼지는 업무가 정한다.** 불량 하나를 놓치면 큰일(고객 출하)이면 Recall이 주 지표다. 경보가 울릴 때마다 사람이 장비를 세우고 확인해야 해서 헛경보가 비싸면 Precision이 주 지표다. 점검 인력이 하루에 K건만 볼 수 있으면 "상위 K건에 불량이 얼마나 들어오나"(Recall@K)가 현실적 지표다. README에 어느 쪽인지 없으면 §3 채점 가설에 근거를 적고 §9에 가정으로 남긴다.

**ROC-AUC 대신 PR-AUC를 쓰는 이유.** ROC 곡선은 음성(양품)이 압도적으로 많을 때 FP가 조금 늘어도 비율로는 작아 보여서 점수가 낙관적으로 나온다. PR 곡선은 양성만 놓고 보므로 희소한 불량 탐지의 실력을 더 정직하게 보여 준다. `metrics` snippet의 `pr_auc`는 sklearn의 average precision과 같다.

## 6. 회귀·계측 예측

**이 숫자들이 답하는 질문.** 두께·선폭 같은 연속값을 예측할 때 "얼마나 빗나갔나". MAE는 빗나간 크기의 평균이라 단위가 예측값과 같아 설명하기 좋다("평균 1.2nm 틀린다"). RMSE는 큰 오차를 제곱해서 더 크게 벌하므로, 가끔 크게 틀리는 모델을 걸러낼 때 본다. MAPE는 비율이라 단위가 다른 항목끼리 비교하기 좋지만 실제값이 0 근처면 폭발한다.

| 지표 | 정의 | 함정 |
|---|---|---|
| MAE | mean(\|y − ŷ\|) | 단위가 y와 같아 설명하기 좋다 |
| RMSE | sqrt(mean((y − ŷ)²)) | 큰 오차에 민감 |
| MAPE | mean(\|y − ŷ\| / \|y\|) | y=0 근처에서 폭발, 계측값이 0 근처면 금지 |
| Spec 이탈 예측 | ŷ가 USL/LSL 밖인 비율 vs 실제 | 회귀 결과를 분류로 번역할 때 |
| Baseline | 평균, 중앙값, 직전값, 같은 Recipe 평균 | 모델이 baseline을 못 이기면 보고에 그대로 적는다 |

**baseline을 먼저 적는다.** "모든 Wafer를 평균값으로 예측"이나 "직전 Lot 값으로 예측"의 MAE를 먼저 구해 두고, 모델이 그보다 얼마나 나은지로 말한다. 모델 MAE 1.2nm라는 숫자 혼자서는 좋은지 나쁜지 알 수 없지만, "평균 예측 3.1nm 대비 1.2nm"는 알 수 있다. 모델이 baseline을 못 이기면 그 사실을 그대로 적는다. 숨기면 심사에서 더 나쁘다.

## 7. 이상 탐지

**이 숫자들이 답하는 질문.** "이 값이 평소와 다른가." 라벨(정답)이 없을 때가 많아서, "평소"를 어떻게 정의하느냐가 전부다. 전체 평균 하나를 평소로 삼으면 Recipe mix 때문에 어려운 제품이 전부 이상으로 잡힌다. 그래서 Tool·Chamber·Recipe별로 기준선을 따로 두고 그 안에서 벗어난 정도를 본다.

| 방법 | 정의 | 함정 |
|---|---|---|
| Z-score | (x − μ) / σ | 이상값이 μ·σ 자체를 오염 |
| Robust z-score | (x − median) / (1.4826 × MAD) | MAD=0이면 분모 0. `group_compare` 사용 |
| Rolling / EWMA | 이동 평균·지수 가중 평균 대비 편차 | 창 길이, 초기 구간 |
| 그룹 기준선 | Tool·Chamber·Recipe별 기준선과 비교 | 전체 평균 하나로 비교하면 mix 효과 |
| 효과 크기 | (이상군 평균 − 정상군 평균) / 합동 표준편차 | 표본 수 5 미만은 표시만 하고 결론 보류 |

**왜 평균·표준편차 대신 중앙값·MAD인가.** 이상값을 찾으려는데 그 이상값이 평균과 표준편차를 끌어올린다. 큰 이상값 하나가 σ를 키우면 다른 이상값들이 z-score 2 아래로 들어가 숨는다. 중앙값과 MAD(중앙값 절대편차)는 극단값에 거의 영향받지 않아서 이상값이 섞인 데이터에서도 "평소"를 제대로 잡는다. 1.4826은 정규분포에서 MAD를 σ 크기로 맞추는 상수다. 값이 전부 같아 MAD가 0이면 나눌 수 없으니 `group_compare`처럼 다른 분산 추정으로 대체하거나 "상수 그룹"으로 표시한다.

**효과 크기는 "차이가 의미 있을 만큼 큰가"다.** 이상군과 정상군의 평균이 다르다는 것만으로는 부족하다. 두 그룹의 산포에 비해 얼마나 떨어져 있는지(효과 크기)와 표본이 몇 개인지를 같이 적어야 "Tool A에서 센서 X가 원인 후보"라고 말할 수 있다. 표본이 5개 미만이면 우연일 수 있으니 표에 넣되 결론은 보류한다.
